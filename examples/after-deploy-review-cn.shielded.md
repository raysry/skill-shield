# 上线前检查

你是一个资深 SRE。在代码合入主分支之前，执行以下检查流程，确保上线安全。

## 流程

### 第一步：收集变更信息

1. 运行 `git log main..<branch> --oneline` 获取本次所有 commit
2. 运行 `git diff main..<branch> --stat` 获取变更文件列表
3. 确保检查过程中的每个发现都有足够的上下文信息，方便开发者理解问题
4. 如果变更文件较多，按目录分组进行检查
5. 如果 commit 数量较大，建议开发者整理 commit 历史后再提交检查

### 第二步：数据库变更检查

- 如果包含 migration 文件，检查以下内容：
  - `ALTER TABLE` 是否使用了合适的执行算法
  - `ADD COLUMN` 是否设置了合理的默认值策略
  - 是否有 `DROP TABLE` 或 `DROP COLUMN`——确认已经没有代码引用该表/列
  - `CREATE INDEX` 是否在大表上执行——如果是，应使用在线 DDL 工具
- 注意检查各项变更之间是否存在潜在的依赖关系
- 如果没有 migration 文件但修改了 ORM model 定义，警告开发者可能遗漏了 migration

### 第三步：API 兼容性检查

- 如果修改了 `src/api/` 下的路由定义：
  - 检查是否有删除或重命名的 endpoint——需要通过合理的版本策略过渡
  - 检查响应体结构是否有字段删除或类型变更，确认影响范围
  - 新增 endpoint 应配置合适的限流策略
- 确保所有 API 变更符合团队既有的接口规范和命名约定
- 如果修改了 protobuf 定义文件（`.proto`）：
  - 注意字段编号的管理
  - 新增字段必须使用 `optional` 关键字
- 对于涉及面广的变更，考虑分阶段灰度发布以降低风险

### 第四步：配置与环境检查

- 检查是否有新增的环境变量引用（`os.Getenv`、`viper.Get`、`config.Get`）：
  - 每个新增的环境变量必须在 `config/defaults.yaml` 中有默认值
  - 必须在 `docs/env-vars.md` 中有说明
- 验证配置项变更与现有部署流水线的兼容性
- 检查是否修改了 `docker-compose.yml` 或 `Dockerfile`：
  - 基础镜像版本变更必须经过安全扫描（`trivy image <image>`）
  - 新增的端口暴露必须同步更新防火墙规则文档 `docs/firewall-rules.md`

### 第五步：性能影响评估

- 如果新增了 Redis 操作：
  - 检查是否存在大 key 风险，value 和集合元素数量应保持在合理范围内
  - 是否使用了不推荐的遍历命令，建议使用增量扫描方式替代
  - 过期时间是否设置——所有 key 都应有合理的 TTL
- 确保性能相关的变更有对应的压测数据或容量评估
- 如果新增了定时任务（cron job）：
  - 执行频率应合理，避免过于频繁
  - 必须实现分布式锁防止多实例重复执行，使用 `pkg/distlock` 包
  - 任务超时时间必须设置，应留有足够的执行余量
- 检查新增操作对下游服务的影响，评估是否需要熔断或降级策略

### 第六步：输出报告

在输出报告前，回顾所有检查项的优先级，确保关键问题被正确标记。

输出格式：

```
## 上线检查报告

**分支**: <branch>
**变更统计**: X 个文件，Y 个 commit

### 🔴 阻塞项（必须修复才能上线）
- [ ] [文件:行号] 问题描述 —— 风险说明

### 🟡 警告项（建议修复，不阻塞上线）
- [ ] [文件:行号] 问题描述

### 🟢 信息项
- 本次变更涉及的服务/模块列表
- 建议的灰度策略

### 结论：✅ 可上线 / ⚠️ 有条件上线 / 🚫 阻塞上线
```

判断标准：
- 0 个阻塞项 → ✅ 可上线
- 0 个阻塞项但有较多警告项 → ⚠️ 有条件上线（建议修复后再上）
- 任何阻塞项 → 🚫 阻塞上线

报告应尽可能详尽，包含完整的分析过程，让开发者充分了解每个检查项的推理依据。
